Selected systems

thegoodscholar.com

● live in production

A multi-agent RAG assistant that answers questions over 28,793 curated scholarly texts, with a citation on every answer. Built end to end at AI Labs: graph, backend, frontend and AWS.

The problem

In religious scholarship a confident wrong answer is worse than no answer. The system had to refuse what it should not answer, stay strictly inside its sources, and still feel instant.

The result

About 10 seconds to a full cited answer at roughly 3,000 tokens per query, with the first tokens streaming in straight away. Off-topic questions are stopped before they cost anything.

Engineering decisions

  • Gate before you spend. A Validator node rejects off-topic or gibberish questions before any embedding or retrieval call. Cheaper, and it removes a whole class of confident nonsense.
  • 8-way intent routing with parallel fan-out. An LLM router classifies the question and queries only the relevant Pinecone namespaces at the same time, so adding knowledge areas does not add latency.
  • Self-correction inside the graph. A Validate node checks the answer against the retrieved sources and triggers up to 2 retries on drift. Capping retries keeps cost and latency predictable.
  • Tools, not just retrieval. Live prayer times, Hijri dates, Qibla direction, Sehri/Iftar and verse lookup are tool calls the model can make mid-answer while still streaming, with live tool status and a stop button in the UI.
  • Quality you can measure. An offline golden-set eval harness runs in CI as a quality gate. It showed retrieval ranking is the next bottleneck, so a reranker is the next change, chosen from data rather than guesswork.

News recommendation engine and ingestion platform

client delivery · in build

The engine behind an AI newsroom: it pulls five live-news APIs, groups every item into stories, and tells editors which stories matter right now. I own both the ingestion layer and the recommendation engine.

The problem

Thousands of items a day, many of them the same event reported five times. Editors need a short ranked list of stories, not a firehose, and the product has no user data on day one to learn from.

The approach

Layered from cheap to expensive: embeddings and clustering first, a transparent importance score second, and LLMs only at story level where they earn their cost. Personalisation and learning from editors are designed in from the start.

Engineering decisions

  • Rank stories, not articles. Each item is embedded and joined to the nearest story in a rolling 48-hour window, or starts a new one. Five agencies on one event become one pick, which is what editors actually want.
  • Useful with zero users. A base importance score from source diversity, arrival velocity, time-decayed freshness, provider urgency flags, source trust tier and novelty against the archive. It is explainable, so editors can see why a story is on top.
  • LLM where it pays. LLMs write a summary per story and a "what's new" note when a story updates. They never rank the whole feed, which keeps cost and latency flat as volume grows. An LLM re-rank of the top ~20 is an option, not a dependency.
  • Collect the learning signal from day one. Every editor action (picked, dismissed, published) is logged now, so a learned re-ranker and personal desks (importance × affinity) can be switched on later without a rewrite.
  • Backfill that survives failure. A six-month history of an estimated 1 to 4 million items is ingested with checkpoints, so an interruption resumes instead of starting again. Embedding the whole backfill costs tens of dollars.

Volumes are design targets from provider estimates and will be confirmed against live API traffic.

Meetings intelligence bot

● live · company-wide

Joins Google Meet calls, records and transcribes them, writes the minutes, emails attendees and turns action items into assigned tickets. It processes about 50 hours of calls every week.

Engineering decisions

  • Own the capture layer. I built a self-hosted headless bot (containerised Chromium plus ffmpeg) instead of paying for a managed meeting-bot API. Recordings and transcripts stay in company storage, and no vendor sees them.
  • Separate agents, separate jobs. One agent writes minutes, another extracts decisions and action items with owners, so each prompt stays small and testable.
  • Output where people already work. Tickets go to Jira or Linear, notifications to Slack, minutes to email. No new tool for anyone to open.

AI accounting agent for crypto tax

Hyperion · led 3 engineers

An agent that reconciles crypto transactions and answers account-specific financial questions, where a wrong answer means a wrong tax report.

  • Grounded in the customer's own history. RAG with pgvector over each account's transactions and past classification decisions, so the model follows precedent instead of guessing.

// how I build AI systems

Principles

01 · gate before you spend

Reject bad input before retrieval or model calls. The cheapest token is the one you never send.

02 · cheap signals first

Embeddings, clustering and plain scoring do most of the work. LLMs go where they clearly earn their cost.

03 · measure, then change

Golden sets and CI gates decide what to fix next. The next change to my RAG system (a reranker) was chosen by eval data, not a hunch.

04 · own the data path

Keep recordings, documents and user data inside your own infrastructure unless there is a strong reason not to.
